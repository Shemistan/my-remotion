# Данные на внешнем SSD через `MS_DATA_DIR` под защитой StorageGuard

**Контекст.** На системном диске свободно 61 ГБ (занято 87 %), на внешнем SSD
`/Volumes/External SSD` — 211 ГБ. Человек решил хранить проекты, исходные видео,
промежуточные файлы, рендеры и экспорты на внешнем SSD, отдельно от каталога моделей,
без жёсткой привязки к диску; при отключении диска не терять данные и не переключаться
незаметно на системный диск. На macOS путь `/Volumes/<имя>` при отключённом диске
исчезает, и `mkdir -p` создал бы его на системном томе.

**Решение.** Все данные (`studio.db`, `workspace/`, `cache/`, `logs/`) — в `MS_DATA_DIR`,
переменная обязательна, значения по умолчанию нет. Предлагаемое значение —
`/Volumes/External SSD/MotionStudio`. Корень создаёт только `doctor --init`, записывая
маркер тома `.motion-studio-store.json`. StorageGuard перед стартом, перед каждой задачей
и периодически во время неё проверяет: маркер и `store_id`, Volume UUID, отличие
устройства от системного тома (если не задан `MS_ALLOW_SYSTEM_DISK=1`), запись,
свободное место. При сбое — режим `storage_offline`: задачи не берутся, текущие
возвращаются в `pending`, API отвечает 503 (`docs/architecture/03-target-architecture.md` §5.1).

**Последствия.** Без подключённого SSD приложение не работает — это осознанно.
БД и медиа всегда на одном томе, поэтому атомарный `rename` и согласованность
сохраняются. Перенос на другой диск — копирование каталога и смена `MS_DATA_DIR`
(маркер переносится вместе с данными; `doctor --adopt` явно перезаписывает в нём
Volume UUID нового тома).

**Уточнения реализации (2026-10-21, H2).** Под нагрузкой (параллельные рендеры и агенты)
`diskutil` отвечает дольше прежнего таймаута в 5 с. Сторож принимал это за потерю диска и
ронял задачи с `storage_unavailable`, хотя SSD был подключён. Теперь VolumeUUID
сверяется через `diskutil` один раз на процесс и снова — только при смене опознания тома
(точка монтирования, st_dev, корень). Между сверками живость проверяют дешёвые вызовы:
stat корня, чтение маркера, пробная запись, statfs. Отказы делятся на два класса.
Окончательные: корня нет, маркер чужой, другой том, st_dev сменился, запись не прошла.
По ним offline объявляется сразу. Неокончательные: проба тома не ответила
(`volume_probe_failed`) или проверка не уложилась в дедлайн (`storage_watch_timeout`).
По ним offline объявляется после 3 таких отказов подряд; повисшая насовсем проверка даёт
offline примерно через 120 с при интервале 10 с. Системный диск по-прежнему не
используется никогда.
