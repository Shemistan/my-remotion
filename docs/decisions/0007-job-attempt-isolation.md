# Изоляция попыток задач и дочерних процессов

**Контекст.** ADR 0006 переводит приложение в `storage_offline` и останавливает дочерние
процессы, но не требует подтвердить, что они завершились, прежде чем задача снова
станет `pending`. Есть и другие пути к двум одновременным исполнителям одной задачи:
падение сервера оставляет «сирот» (`claude`, Chrome, `ffmpeg`); второй экземпляр
сервера или CLI на том же `MS_DATA_DIR`; процесс, зависший в непрерываемом вводе-выводе
на отключённом диске, не реагирует на SIGKILL. Требование человека: повторный запуск
задачи недопустим, пока предыдущий процесс не завершён или не изолирован.

**Решение.**

1. **Один владелец хранилища.** Сервер и CLI при старте берут эксклюзивную
   блокировку ОС на `MS_DATA_DIR/run/owner.lock` (POSIX `fcntl`-lock, через
   SQLite `locking_mode=EXCLUSIVE` + `BEGIN EXCLUSIVE`). Ядро снимает её само при
   смерти процесса, поэтому «брошенной» блокировки не бывает и гонки при её захвате
   нет. Рядом `run/owner.json` (pid, время старта процесса, вид — server/cli) —
   только для диагностики: кто держит хранилище. Не взял блокировку — второй
   экземпляр не стартует.
2. **Fencing-токен попытки.** Захват задачи увеличивает `jobs.attempt` в транзакции.
   Каждая попытка пишет только в свой draft `drafts/<job>-a<attempt>/`. Публикация
   версии и запись результата проходят, только если `attempt` попытки равен текущему
   `jobs.attempt` (проверка в той же транзакции). Устаревшая попытка ничего не может
   опубликовать, даже если её процесс жив.
3. **Реестр процессов.** Каждый дочерний процесс запускается в своей группе
   (`detached: true`) и до начала работы записывается в `job_processes`
   (`job_id, attempt, pid, pgid, started_at, cmd`); сервер держит копию реестра в памяти
   на время `storage_offline`.
4. **Условие повторного запуска.** Retry, восстановление после рестарта и выход из
   `storage_offline` переводят задачу в `pending` только после того, как все процессы
   прежней попытки подтверждённо завершены: живые получают SIGTERM на группу, через 5 с —
   SIGKILL, затем ожидание выхода до 30 с. Если завершение не подтверждено, задача
   получает статус `blocked` (причина `stale_process`), её прежняя попытка аннулирована
   токеном, draft помечается `.quarantined` и не переиспользуется. Автоматического
   перезапуска нет; UI показывает PID и команду, повтор — только действием человека после
   исчезновения процесса.
5. **Порядок при старте сервера:** owner-lock → StorageGuard → разбор реестра процессов
   → восстановление задач → только затем захват новых задач.

**Утверждение (2026-10-20).** Принято человеком с требованием надёжной реализации:
один владелец с атомарной блокировкой ОС; группы процессов и реестр; draft на
попытку; fencing-токен; корректное завершение процессов; восстановление после
рестарта; запрет автоповтора без подтверждённого завершения; карантин
неоднозначных результатов; конфликтующие операции над одной сценой не идут
параллельно (замок сцены в оркестраторе). Всё подтверждается автотестами
(`09-acceptance-tests.md` §5).

**Уточнения реализации (2026-10-21, Task 13).** Возврат из `storage_offline` — не
прерывание: `interrupts` не растёт (повторы ограничивает человек). Повтор задачи человеком
обнуляет `interrupts`. Подробно — rulings п. 20–21.

**Уточнения реализации (2026-10-23, S5).** Внутри попытки может идти второй дубль сцены:
он пишет только в `run/tmp/<job>-a<attempt>/take2` (и `qa-t2`) — каталог той же попытки, а
не draft; снимки оценённых попыток — в `run/tmp/<job>-a<attempt>/attempts/<n>`. Публикуется
одна лучшая попытка, восстановленная в draft, с fencing, как прежде. Процессы обоих дублей —
в реестре этой попытки; рендеры помечают свой Chrome ключом `renderId` (имя `run/tmp`
рендера), и уборка после рендера закрывает только свои записи. Исключение или жёсткий выход
первого дубля отменяет второй, и попытка ждёт его конца. Второй дубль допускается, только
если `spent + reserved + 2 × цена попытки ≤ лимит задачи` (цена попытки — Engineer и Visual
QA оценённой попытки первого дубля; rulings 2026-10-23): лучше не начинать дубль, чем не
дойти до оценки. Сбой второго (кроме хранилища и
отмены задачи) задачу не роняет — при неподтверждённой смерти его процесса `take2` и
`qa-t2` не удаляются до разбора: после итога цикла попытка разбирается (`reapAttempt`;
процессы первого дубля к этому моменту подтверждённо мертвы), чисто — каталоги убираются,
нет — остаются, в предупреждениях PID, неуспешный итог уходит в карантин.

**Последствия.** Две живые попытки одной задачи не могут писать в одно место и не
могут обе опубликовать результат. Добавляются статус задачи `blocked` (расширение
списка ТЗ §4.2), таблица `job_processes` и каталог `run/`. В вертикальном срезе без
БД действуют owner-lock, группа процессов и реестр в файлах `run/processes/`.
