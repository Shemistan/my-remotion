## 1. Продукт и цели

Создать **AI Motion Studio** — локальную систему, которая помогает превратить отснятое talking-head видео в YouTube-ролик с выразительной, плавной, динамичной и осмысленной motion-графикой продуктового уровня.

Продукт имеет **два режима**, использующих общий движок генерации сцен:

1. **AI Video Production:** импорт видео → транскрибация → неразрушающий черновой монтаж → смысловой и визуальный анализ → план анимаций → утверждение → генерация и QA → утверждение сцен → финальная сборка.
2. **Motion Playground:** генерация самостоятельной анимации по текстовому запросу → предпросмотр → редактирование через чат → версионирование → экспорт и возможность вставить сцену в видеопроект.

**Основной тип видео:** talking head. **Способ визуализации:** автоматически выбирать между overlay, fullscreen, split-screen, picture-in-picture, callout и отсутствием графики. **Режим автономности:** AI предлагает и исполняет, пользователь утверждает монтаж, визуальный план и готовые сцены. **Первичный агентный runtime:** Claude Code CLI/subagents, через заменяемый адаптер.

### 1.1. Продуктовые принципы

- Визуализировать **смысл речи**, а не добавлять эффекты ради эффектов.
- Обеспечивать единую дизайн-систему видео и выразительную, но контролируемую анимацию.
- Уметь выбирать «без графики», если это лучше для зрителя.
- Использовать существующие библиотеки и локальные модели, а не дублировать их.
- Хранить исходники сцен, версии, параметры, превью и ссылки на источники.
- Сохранять контроль человека на критических этапах.
- Система должна переживать перезапуск, продолжать задачи и воспроизводить экспорт.
- Нельзя гарантировать вирусность или удержание; можно улучшать понятность, ритм, качество подачи.

### 1.2. Не входит в первоначальный MVP

Полноценная замена Premiere/DaVinci, коллаборативный редактор, облачный SaaS, автопубликация на YouTube, обучение собственных моделей, обязательная векторная БД, генерация музыки, продвинутый color grading и сложный многокамерный монтаж.

## 3. Целевая архитектура

Три логических слоя (физическое разбиение на сервисы определить после аудита):

```text
Web UI: Projects | Motion Playground | Transcript | Timeline | Scene Inspector
                                  |
                     Production Control API
                                  |
                    Persistent Job Orchestrator
                     /           |           \
            Agent Runtime    Knowledge Adapter    Media Services
            (Claude Code)   (my-remotion)          (ai-platform)
                     \           |           /
                   Scene Package + Version Store
                                  |
                     Remotion + FFmpeg Workers
                                  |
                       Previews / Final Exports
```

### 3.1. Production Control Plane

Проекты, состояния задач, медиа, approvals, таймлайн, чат, версии сцен, прогресс, отмена/повтор, логи, настройки и экспорт.

### 3.2. Agent Intelligence Plane

Заменяемый `AgentRuntimeAdapter`, оркестрация ролей, типизированные входы/выходы, управление контекстом и правами, ограничение итераций, контроль стоимости и параллельности.

### 3.3. Media Execution Plane

ASR через существующий сервис; FFmpeg/ffprobe для подготовки, EDL, прокси и сборки; Remotion для покадровой графики и рендера. Тяжёлые задачи выполняются асинхронно и сохраняют прогресс.

### 3.4. Рекомендации по стеку (не безусловный приказ)

- React + TypeScript для интерфейса, с переиспользованием существующего UI.
- TypeScript на уровне генератора сцен и контрактов.
- Remotion для композиции; FFmpeg для медиаопераций.
- SQLite для локального MVP либо существующая БД ai-platform; выбор обосновать.
- Очередь задач на базе уже существующей инфраструктуры либо минимальный durable job runner.
- Локальная файловая система для больших медиа + БД для метаданных.
- Zod/JSON Schema для валидации межагентных контрактов.
- Точное средство запуска Claude Code выбирать после проверки доступного CLI/SDK, условий использования и безопасности.

Не добавлять Redis, Kubernetes, микросервисы и векторную БД без доказанной необходимости.

## 4. Роли агентов и границы ответственности

**Важно:** «роль» не обязательно означает отдельную LLM-сессию. Свести роли в минимум процессов, необходимый для качества. Все роли возвращают структурированные результаты с ссылками на входные артефакты.

| Роль | Вход | Результат | Примечание |
|---|---|---|---|
| Transcript Analyst | ASR, медиа | транскрипт с таймкодами и confidence | ASR вызывает обычный сервис |
| Rough Cut Editor | транскрипт, аудио | EDL предложений удаления | не удалять осмысленные паузы |
| Footage Analyzer | ключевые кадры | безопасные зоны, автор, объекты, движение | не делать вывод по одному кадру |
| Semantic Director | утверждённый rough cut | главы, тезисы, сущности, смысловые якоря | различать факты и предположения |
| Visual Director | семантика, footage | кандидаты сцен и композиции | разрешено «нет графики» |
| Art Director | тема, предпочтения | Style Bible | согласованность всего ролика |
| Knowledge Researcher | brief сцены | компоненты, пути, лицензии, ограничения | индекс → карточка → исходник |
| Motion Director | brief, style, timing | покадровая постановка, камера, easing | ритм, иерархия, синхронизация |
| Remotion Engineer | motion spec, refs | исполняемая композиция и props | детерминированность |
| Visual QA | превью, кадры, спецификация | технический/визуальный/семантический отчёт | реальные рендеры, не только код |
| Production Supervisor | состояния, QA | координация, решения о retry | ограничение затрат и циклов |

### 4.1. Доступ к Knowledge Base

- Semantic Director: не нужен доступ к исходникам компонентов.
- Visual Director: таксономия и краткий каталог.
- Art Director: стиль и референсы.
- Knowledge Researcher: каталог, технические карточки, пути к источникам.
- Motion Director: паттерны движения и выбранные возможности.
- Remotion Engineer: конкретный исходник, официальный Remotion skill, ограничения.
- QA: style, brief, motion spec и реальные кадры.

### 4.2. Оркестрация

- Роли с независимыми входами могут исполняться параллельно.
- Не допускать одновременного изменения одной версии сцены несколькими агентами.
- На каждый шаг: `pending → running → completed | failed | cancelled | awaiting_approval`.
- Ограничить количество автоматических исправлений (начальное значение: 2, конфигурируемое).
- Ошибка одного рендера не должна уничтожать проект или блокировать остальные сцены.
- Поддержать идемпотентность и повторные запуски.

## 5. Режим A: AI Video Production

### Stage A1. Импорт

- Загрузка исходного видео; оригинал неизменяем.
- ffprobe: FPS, длительность, размеры, кодеки, дорожки, rotation, VFR.
- Прокси для быстрого предпросмотра, waveform, thumbnails.
- Создание проекта, storage paths, media manifest.
- Проверка свободного места и корректная обработка ошибок.

**Выход:** `MediaAsset`, `Project`, `Proxy`, `Waveform`.

### Stage A2. Транскрибация

- Вызвать реальный ASR из `ai-platform`.
- Сохранить сегменты и, если поддерживается, слова с таймкодами и confidence.
- Если word-level timing отсутствует, предусмотреть отдельное выравнивание либо честно обозначить ограничения.
- Позволить пользователю исправлять текст без потери связи с таймкодами.
- Сохранять исходную и исправленную версии.

**Выход:** `Transcript`.

### Stage A3. Черновой монтаж

- Находить длинные паузы, оговорки, повторы, неудачные дубли.
- Формировать предложения с причиной, интервалом и уверенностью.
- Показывать пользователю удаляемые фрагменты и возможность восстановить.
- Применять только после подтверждения (**Approval A**).
- Сохранять неразрушающий EDL и точное соответствие source ↔ edited time.
- Обеспечить smooth cut без потери смысла и грубых аудиостыков; не обещать автоматическую идеальность jump cuts.

**Выход:** `EditDecisionList`, `EditedTimeline`, `RoughCutPreview`.

### Stage A4. Семантика и видеоряд

- Semantic Director: главы, тезисы, сложные концепции, числа, причинно-следственные связи, сущности, смысловые якоря.
- Footage Analyzer: положение автора, лица/рук, важные предметы, движение, свободные зоны по нескольким кадрам.
- Привязать выводы к **edited timeline**.
- Отдельно отметить неопределённость и спорные места.

**Выход:** `SemanticTimeline`, `FootageAnalysis`.

### Stage A5. Visual Planning и Style Bible

Для каждого кандидата сцены:

- Почему она нужна, какую мысль объясняет.
- Режим: `overlay | fullscreen | split_screen | pip | callout | none`.
- Начало/конец и смысловые якоря.
- Визуальная метафора, пример композиции, уровень сложности.
- Важные слова/числа, которые должны появиться в нужный момент.
- Ограничения: безопасные зоны, лицо, жесты, объекты, читаемость.
- Предварительная оценка полезности, трудоёмкости и визуальной нагрузки.

Создать `StyleBible`: цвета, шрифты, сетка, safe margins, размеры, тени, скругления, motion curves, интенсивность, принципы камеры и переходов.

Показать пользователю план на таймлайне: принять/отклонить/изменить/добавить (**Approval B**).

**Выход:** `ApprovedVisualPlan`, `StyleBible`.

### Stage A6. Motion Preproduction

Для утверждённых сцен:

1. Поиск в Knowledge Base.
2. Выбор паттерна и конкретных компонентов с указанием происхождения.
3. Проверка статуса совместимости и лицензии.
4. Постановка движения: beat sheet, keyframes, easing, camera, entrance/hold/exit.
5. Точное согласование с таймкодами слов/сегментов.
6. Выбор стратегии реализации: reuse / adapt / build from scratch.

**Выход:** `MotionSpecification`, `ComponentSelection`.

### Stage A7. Генерация, рендер, QA

- Генерировать самостоятельный Scene Package.
- Сначала TypeScript/build/runtime проверки, затем короткий preview render.
- Визуально проверять несколько ключевых кадров, при необходимости видео целиком.
- QA: композиция, текст, отсутствие clipping, читаемость, ритм, смысл, стиль, синхронизация.
- При проблеме возвращать структурированное замечание на исправление; максимум 2 автоматических retry по умолчанию.
- Сохранять failed previews и логи, не выдавать ошибку за успех.

**Выход:** `SceneVersion`, `Preview`, `QAReport`.

### Stage A8. Пользовательское ревью

На таймлайне пользователь может:

- Включить предпросмотр сцены в контексте исходного видео.
- Принять, отклонить или отправить на исправление.
- Редактировать параметры и чат-промпт.
- Сменить overlay/fullscreen/PiP и поправить размещение.
- Вернуться к любой предыдущей версии.
- Скачать сцену отдельно.
- Переместить сцену по времени; система проверяет смысловую привязку.

**Approval C:** только утверждённые сцены включаются в финальную сборку по умолчанию.

### Stage A9. Финальная сборка

- Применить утверждённый EDL.
- Композировать исходное видео и motion-графику в правильных временных координатах.
- Сохранить исходную речь, избегать рассинхронизации и неожиданного изменения громкости.
- Выполнить final render и техническую проверку результата.
- Экспортировать MP4 H.264/AAC, с выбором FPS/разрешения/качества.
- Отдельный экспорт сцен: MP4 без alpha; для прозрачности — совместимый codec/container с alpha, если поддерживается окружением.
- Сохранить manifest и повторно открываемый проект.

## 6. Режим B: Motion Playground — первый MVP

### 6.1. Основной сценарий

1. Пользователь вводит запрос на русском или английском.
2. Система уточняет только действительно недостающие параметры; иначе использует проектные defaults.
3. Агент определяет визуальную концепцию и ищет подходящие паттерны/компоненты.
4. Создаёт Motion Spec и Remotion Composition.
5. Рендерит предпросмотр.
6. Показывает плеер, параметры, использованные компоненты и статус QA.
7. Пользователь пишет изменение в чат.
8. Система модифицирует текущую сцену, создавая новую версию.
9. Можно сравнить, восстановить или экспортировать любую версию.
10. Готовую сцену можно использовать в Video Production.

### 6.2. Интерфейс

**Слева:** чат, история изменений, выбранные компоненты, параметры и статус генерации.  
**Справа:** видеоплеер/preview, play/pause, seek, frame step, aspect ratio, FPS, duration, background, цветовая тема, кнопки Render/Export.  
**Снизу (минимально):** простой таймлайн одной сцены и версии. Не строить полный NLE в Phase 1.

### 6.3. Версии

- Версии иммутабельны.
- Новая версия содержит parent ID, prompt, diff/изменённые файлы, props, assets, QA и preview.
- Восстановление старой версии не удаляет новую историю.
- «Верни v2, но сохрани новые цвета» создаёт новую версию от указанной базы.
- Внутренний рендер должен воспроизводиться по сохранённым файлам и зависимостям.

### 6.4. Настройки

`aspect_ratio`, `resolution`, `fps`, `duration`, `style_preset`, `color_palette`, `font`, `animation_intensity`, `background`, `transparent_export` (только при поддержке), `safe_area`.

### 6.5. Готовность MVP

Пользователь может создать, посмотреть, исправить, восстановить и экспортировать **реальную** Remotion-сцену, используя индексированную Knowledge Base. Mock-ответы не засчитываются.

## 7. Scene Package и модель данных

**Scene Package** — основная единица производства и версионирования.

```text
workspace/
  projects/<project-id>/
    source/
    proxy/
    transcript/
    edits/
    style/
    timeline.json
    scenes/<scene-id>/
      brief.json
      motion-spec.json
      knowledge-refs.json
      versions/<version-id>/
        src/
        props.json
        assets/
        preview.mp4
        qa.json
        manifest.json
      approved.json
    exports/
```

**Обязательные сущности:** `Project`, `MediaAsset`, `Transcript`, `TranscriptWord`, `EditDecision`, `Timeline`, `TimelineClip`, `SemanticChapter`, `VisualOpportunity`, `FootageAnalysis`, `StyleBible`, `ScenePlan`, `MotionSpecification`, `KnowledgeReference`, `Scene`, `SceneVersion`, `RenderJob`, `QAReport`, `AgentRun`, `Approval`, `ExportJob`.

### 7.1. Таймкоды

Хранить `source_time`, `edited_time`, `scene_local_time`; использовать целочисленные timestamp units, FPS как рациональное значение при необходимости. Поддерживать VFR исходники. Смысловые события привязывать к ID слов/сегментов, а не только к абсолютным секундам. Изменение EDL инвалидирует затронутые привязки и запускает перепроверку, но не безусловную перегенерацию всех сцен.

### 7.2. Пример Scene Plan

```json
{
  "scene_id": "scene_001",
  "start_ms": 12400,
  "end_ms": 17800,
  "purpose": "Объяснить рост пользователей",
  "visual_type": "animated-chart",
  "composition_mode": "overlay",
  "style_id": "project-default",
  "narration_segment_ids": ["seg_012", "seg_013"],
  "status": "proposed"
}
```

### 7.3. Пример Motion Spec

```json
{
  "scene_id": "scene_001",
  "fps": {"numerator": 30, "denominator": 1},
  "duration_frames": 162,
  "beats": [
    {"start_frame": 0, "end_frame": 25, "action": "title-entrance"},
    {"start_frame": 20, "end_frame": 125, "action": "chart-growth"},
    {"start_frame": 125, "end_frame": 162, "action": "hold-and-exit"}
  ]
}
```

Создать реальные типы и схемы валидации; приведённые JSON — примеры, не окончательный контракт.

## 8. Motion Design Standards

### 8.1. Визуальная иерархия

Одна основная мысль в сцене. Чёткие акценты, безопасные поля, разумные отступы, читаемый текст. Не закрывать лицо, руки и важные объекты. Не делать fullscreen там, где автор должен оставаться визуальным центром.

### 8.2. Анимация

- Покадровая, детерминированная, синхронизированная с narration beats.
- Использовать `useCurrentFrame()`, `useVideoConfig()`, `interpolate()`, `spring()` и подходящие Remotion APIs.
- Не полагаться на CSS transitions, hover, scroll и неконтролируемый `requestAnimationFrame`.
- Контролировать easing, overshoot, длительность входа/удержания/выхода.
- Камера, параллакс, глубина и частицы только когда они помогают смыслу.
- Не использовать одинаковый эффект появления для всех объектов.
- Поддержать конфигурируемую интенсивность движения.

### 8.3. Style Bible

Сохранять проектные tokens: цвет, типографика, размеры, сетка, safe zones, карточки, тени, свет, глубина, camera behavior, motion curves, переходы. Все сцены используют эти tokens, если пользователь явно не переопределил.

### 8.4. Сцены и паттерны

Поддержать как минимум: animated counters, growth charts, comparisons, timelines, process flows, network diagrams, technical architecture, UI walkthroughs, code animations, callouts, kinetic typography, conceptual metaphors, fullscreen explainers, overlays и PiP. Не ограничивать систему только этими шаблонами.

### 8.5. Качество

Технический gate: typecheck, корректные зависимости, успешный render, длительность и размеры.  
Визуальный gate: keyframes/screenshots, clipping, контраст, читаемость, плавность, отсутствие артефактов.  
Семантический gate: соответствует фразе и помогает пониманию.  
Style gate: соответствует общему визуальному языку.  
Автоматический QA — вспомогательная оценка, не гарантия качества; окончательное решение за пользователем.

## 9. Интеграция Knowledge Base

Реализовать `KnowledgeAdapter` с операциями (имена примерные):

- `searchCapabilities(query, filters)`.
- `getCapability(id)`.
- `getComponentCard(id)`.
- `getSourceReference(id)`.
- `getVisualPatterns(intent)`.
- `getCompatibility(id)`.

Пайплайн: **смысл → визуальный паттерн → кандидаты → ограничения/лицензия → конкретный исходник → адаптация → тест**.

Каталог должен возвращать `repository`, `commit`, `license`, `source_path`, `documentation_path`, `compatibility_status`, `tested_status`, `confidence` (где возможно). Отсутствующие данные явно помечать `unknown`.

Оригинальные репозитории — только для чтения. Адаптированный код хранить в workspace сцены. Любой код из сторонних источников рассматривать как недоверенный и исполнять только в ограниченной среде.

## 10. Claude Code Runtime и безопасность

Создать `AgentRuntimeAdapter`, который:

- Запускает Claude Code в отдельной рабочей директории.
- Принимает typed task input и возвращает structured output.
- Сохраняет stdout/stderr, статус, время, версию модели, использование токенов (если доступно).
- Поддерживает timeout, cancel, retry, concurrency limit и явный список разрешённых инструментов.
- Не допускает параллельной записи в одну SceneVersion.
- Не использует безусловный bypass permissions.
- Не передаёт секреты в prompts/логи.
- Не позволяет сгенерированному коду обращаться к произвольным сетевым ресурсам или чувствительным путям.
- Проверяет поддерживаемый режим headless/CLI и условия использования до реализации.

Если безопасный запуск Claude Code в данной среде невозможен, документировать проблему и предложить совместимый runtime-адаптер без скрытого обхода ограничений.

## 11. UI и пользовательские сценарии

### 11.1. Разделы

1. **Dashboard:** проекты, статусы, последние экспорты.
2. **Motion Playground:** чат + preview + история версий.
3. **Video Workspace:** плеер, транскрипт, rough cut, главы, визуальный план.
4. **Timeline:** видео/аудио/графика, отметки сцен, изменение времени.
5. **Scene Inspector:** brief, компоненты, props, версии, QA, экспорт.
6. **Knowledge Browser:** поиск паттернов/компонентов и их статуса.
7. **Jobs Monitor:** задачи, прогресс, ошибки, cancel/retry.

### 11.2. Approvals

- **A:** утверждение rough cut.
- **B:** утверждение visual plan.
- **C:** утверждение сгенерированных сцен.
- **Final:** явное действие «Смонтировать / Экспортировать».

После каждого изменения, затрагивающего утверждённый артефакт, корректно сбрасывать или перепроверять зависимые approvals; не допускать незаметной сборки из устаревших версий.

### 11.3. UX ошибок

Показывать понятную ошибку, этап, повтор, технические логи и возможность продолжить с последнего успешного шага. Не скрывать провал рендера под фиктивным preview.

## 12. API, jobs, наблюдаемость

Спроектировать реальные endpoints после аудита существующего backend. Не вводить параллельный API без необходимости.

Минимальные операции:

- Создать/открыть проект.
- Загрузить медиа и получить metadata.
- Запустить/получить ASR.
- Получить/изменить EDL и approvals.
- Сгенерировать visual plan и утвердить.
- Создать/изменить сцену по промпту.
- Получить версии и preview.
- Запустить render/export.
- Получить статус, отменить, повторить job.

Каждый job имеет `id`, `type`, `project_id`, `input_refs`, `status`, `progress`, `attempts`, `started_at`, `finished_at`, `error`, `output_refs`. Предусмотреть recovery после перезапуска и защиту от дублированных запросов.

Логи должны связывать project → scene → version → agent run → render job. Не сохранять секреты и чувствительные данные без необходимости.

### Phase 2 — Video Import + ASR + Rough Cut

**Реализовать:** импорт, прокси, waveform, ffprobe, реальный ASR, редактирование транскрипта, EDL, source↔edited mapping, Approval A, rough-cut preview.

**Приёмка:** исходник не изменяется; удалённые фрагменты можно вернуть; таймкоды после монтажа корректны; проект переживает перезапуск.

### Phase 3 — Semantic & Visual Planning

**Реализовать:** семантический анализ, Footage Analyzer, безопасные зоны, Style Bible, предложения сцен, режимы композиции, Approval B.

**Приёмка:** на talking-head видео система показывает обоснованные предложения сцен с точными таймкодами; пользователь может изменить и утвердить план; графика не планируется автоматически поверх лица без явной причины.

### Phase 4 — Automated Motion Production

**Реализовать:** Knowledge Researcher, Motion Director, Remotion Engineer, QA, batch scene generation, Scene Inspector, чат-правки, Approval C, экспорт отдельных сцен.

**Приёмка:** из утверждённого плана создаётся несколько реально отрендеренных сцен; ошибки одной не ломают остальные; сцены можно исправлять независимо, возвращать версии и утверждать.

### Phase 5 — Timeline Assembly & Final Export

**Реализовать:** сборку rough cut и графики, overlay/fullscreen/PiP, точную синхронизацию, финальный MP4, настройки экспорта, повторное открытие проекта.

**Приёмка:** из исходного talking-head видео и утверждённых сцен получается воспроизводимый финальный MP4 без потери синхронизации; экспорт повторяется из сохранённого проекта.

### Phase 6 — Production Polish (после функционального завершения)

Профили производительности, дизайн-пресеты, улучшенные camera/motion patterns, визуальный QA, шаблонизация лучших сцен, мониторинг затрат, UX-полировка, нагрузочные тесты. Не смешивать с MVP.

## 14. Сквозные приёмочные тесты

### Test 1 — Data Storytelling

**Prompt:** «Создай премиальную анимацию роста пользователей с 10 000 до 1 000 000 за три года. Тёмный фон, крупная типографика, плавное движение графика, акцент на конечном значении».

Проверить: реальный график, числовая анимация, композиция, читаемость, стабильный рендер, экспорт.

### Test 2 — Technical Explainer

**Prompt:** «Покажи архитектуру AI-агента: пользователь отправляет запрос, оркестратор вызывает три инструмента, данные возвращаются обратно. Световые импульсы движутся по связям».

Проверить: смысловая схема, согласованное движение, выбор компонентов из KB, источники, отсутствие перекрытий.

### Test 3 — Iterative Editing

**Prompt после Test 2:** «Уменьши скорость анимации на 25%, сделай карточки более объёмными, сохрани композицию и верни цветовую палитру из первой версии».

Проверить: действительно изменена существующая сцена, история сохранена, предыдущая версия доступна, рендер не регрессировал.

### Test 4 — Talking Head (после Phase 5)

Взять реальный короткий talking-head ролик (например, 60–120 секунд) с паузами, несколькими тезисами и хотя бы одной цифрой. Проверить ASR, rough cut, source↔edited mapping, предложения графики, approvals, сцену overlay и fullscreen, синхронизацию и финальный экспорт. **Тестовое видео должен предоставить пользователь либо разрешить использование безопасного локального тестового материала.**

### Общие требования к тестам

- Сохранять evidence: preview, итоговый файл, логи, отчёт QA.
- Не выдавать mock/stub за завершённую интеграцию.
- Указывать, что проверено автоматически, а что требует визуального утверждения человеком.
- Тестировать восстановление после сбоя и отсутствие порчи оригиналов.

## 15. Риски и меры

| Риск | Мера |
|---|---|
| Claude Code CLI не подходит для фонового запуска | Проверить на Phase 0, использовать адаптер и поддерживаемый режим |
| React-библиотеки не рендерятся детерминированно | Классификация совместимости, адаптация к frame-driven Remotion |
| Сцены выглядят несогласованно | Style Bible, Art Director, Style QA |
| Графика закрывает автора | Footage Analyzer, safe zones, ручная правка |
| Слишком много эффектов | Visual Director может выбрать `none`, глобальная проверка плотности |
| Рассинхронизация после вырезания пауз | EDL, source↔edited mapping, semantic anchors |
| Долгие/дорогие генерации | очередь, лимиты, retries, preview до full render |
| Ошибки в сгенерированном коде | sandbox, typecheck, runtime QA, ограничения зависимостей |
| Неподходящие лицензии | лицензия и provenance каждого компонента, блокировка сомнительных случаев |
| Потеря истории после перезапуска | durable jobs, иммутабельные версии, manifest |
| Неизвестные факты в текущем ТЗ | Phase 0 и явная маркировка assumptions |

## 16. Правила выполнения для Claude Code

1. **Сначала Phase 0.** Не переходи к разработке платформы до согласования архитектуры.
2. Сначала изучай существующие проекты; не создавай дублирующие API, UI и очереди без причины.
3. Не меняй `ai-platform`, `my-remotion` и сторонние репозитории без явного согласования; для Phase 0 достаточно read-only доступа.
4. Не устанавливай зависимости и не запускай тяжёлые модели без необходимости на этапе аудита.
5. Используй небольшой вертикальный срез и проверяй его end-to-end, прежде чем расширять систему.
6. Не обещай визуальное качество только по успешному TypeScript build; рендери и анализируй реальные кадры.
7. Не делай фиктивные API-ответы или placeholder-анимации финальным результатом.
8. После каждой фазы покажи: реализовано, тесты, известные ограничения, что требуется утвердить.
9. Не запускай бесконечные циклы агента; введи лимиты попыток и понятные ошибки.
10. При выборе технологий объясняй trade-offs и минимизируй ненужную инфраструктуру.
11. Сохраняй пользовательские решения, approvals, историю версий и возможность отката.
12. При неопределённости задавай только блокирующие вопросы; остальное документируй как assumptions.
